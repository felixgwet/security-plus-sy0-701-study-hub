Section 07 — Data Protection · SY0-701 Study Notes

Exam objective coverage: 1.4 (cryptographic solutions), 3.3 (compare/contrast data protection concepts & strategies), 4.2 (asset management implications), 4.4 (alerting & monitoring — DLP), 4.5 (DLP configuration), 5.1 (governance) — lessons 59–67. This section is a pure memorization goldmine: classification levels, ownership roles, data states, and DLP types are asked constantly.

1. Data Protection & Classification (3.3)

Data protection = safeguarding important information from corruption, compromise, or loss — ensuring CIA of data.

Classification is based on: ① value to the organization and ② sensitivity if disclosed. The data owner decides the classification level.

⚠️ Overclassifying data wastes money — you end up protecting everything at the highest level (extra personnel, access controls, technical solutions). Classify properly so higher levels get more resources.

Commercial (4 levels, lowest → highest):

LevelImpact if releasedExamples
PublicNoneWebsite content, this course
SensitiveMinimalFinancial data, unreleased course material
PrivateInternal-onlyPersonal records, salary info, SSNs — relates to an individual entity
ConfidentialSeriousTrade secrets, IP, source code; approved personnel + third parties under NDA (e.g., CompTIA exam questions)

Critical data = too valuable to allow any risk if captured; viewing severely restricted (e.g., credit card numbers, access limited to a few trusted individuals).

Government/Military (5 levels, lowest → highest):

LevelDisclosure harmExamples
UnclassifiedNone — releasable to the public, incl. via FOIA requestsPublic info
Sensitive but Unclassified (SBU)Won't hurt national security, but harms the individuals in itMedical records, personal files of soldiers
ConfidentialCould seriously affect the governmentTrade secrets
SecretCould seriously damage national securityMilitary deployment plans, defensive postures
Top SecretCould gravely damage national securityWeapon system blueprints

⚠️ Trap: memorize the affect → damage → gravely damage escalation. SBU is the one that protects *individuals* rather than the nation.

Data lifecycle: policies must define how data is stored, when, how long, and how it's destroyed. Follow local/state/federal retention requirements — some data must legally be kept for set periods.

2. Data Ownership Roles (4.2 & 5.1) — know every role cold
RoleDefinitionKey identifier
Data ownerSenior executive with ultimate responsibility for CIA of the information asset; labels the asset and mandates controlsNOT the file creator; NOT IT
Data controllerEntity deciding the purposes and methods of data collection, storage, usage; guarantees legality; holds ultimate accountability for privacy breaches — cannot delegateThe accountable one
Data processorGroup/individual hired by the controller to collect, store, or analyze data under the controller's directionThe hired hands
Data stewardWorks for the data owner; ensures data quality and metadata; makes sure labeling/classification actually happensQuality + correct labels
Data custodianManages the systems where data is stored (e.g., system administrator); enforces access control, encryption, backup/recovery per the owner's requirementsIT/sysadmin role
Data privacy officerOversees all privacy-related data (PII, SPI, PHI); ensures legal/regulatory compliance, purpose limitations, consent, data minimization, sovereignty, retention; on the hook when a breach exposes user dataPrivacy compliance

⚠️ Biggest trap: who should own data? The business side (department leaders, CFO for accounting data), never IT — IT knows systems, not data context. IT should be custodians.

3. Data States (3.3)
StateMeaningProtection methods
Data at restStored in databases, file systems, storage systems; not movingEncryption + ACLs
Data in transit (a.k.a. in motion)Actively moved across internet/private networkCommunication tunneling: SSL/TLS, VPN, IPsec
Data in useBeing created, retrieved, updated, deletedApplication-level encryption, access controls, secure enclaves

At-rest encryption methods (know the granularity ladder):

  • Full disk — entire hard drive; encrypted when system off, decrypted when logged in
  • Partition — specific partitions only (e.g., the D: drive)
  • File — individual files
  • Volume — a set of selected files/directories
  • Database — at column, row, or table level
  • Record — specific *fields* within a database record (useful when users share one DB with different view rights)

In-use nuance: data must be decrypted to be processed — that's why it's hard to protect. Secure enclaves (e.g., Intel SGX) encrypt data even while it exists in memory so untrusted processes can't decode it.

5. Data Sovereignty (3.3)
  • Data is subject to the laws of the country where it's collected/processed — must be managed, stored, and processed per that country's laws.
  • Cloud computing made this critical (data centers scattered worldwide).
  • GDPR protects EU citizens while within the EU/EEA borders (protection doesn't follow them outside). Any organization handling EU citizens' data must comply regardless of the organization's location — fines are hefty.
  • China and Russia have strict sovereignty laws requiring data to be stored and processed within national borders — a challenge for multinationals using cloud.
  • Know the physical locations of your data centers and cross-border data flows; no illegal transfers from a privacy jurisdiction without consent; cloud services may restrict access from multiple geographies.
6. Securing Data — the eight methods (3.3)
MethodOne-liner
Geographic restrictions (geofencing)Virtual boundaries restricting access by location (e.g., ban logins from Asia/Africa when all employees are in the Americas); helps comply with sovereignty laws
EncryptionPlaintext → ciphertext with an algorithm + key; reversible with the decryption key; protects data at rest and in transit
HashingConverts data to a fixed-size hash value; one-way (cannot be reversed/decrypted); stores passwords, verifies file integrity
MaskingReplaces some/all of a field with placeholders (e.g., X), can keep partial data (area code) and the original format; one-way; a method of de-identification
TokenizationReplaces sensitive data with non-sensitive tokens; original stored securely in a separate database; token is a reference — used in payment processing to protect credit card numbers
ObfuscationMakes data unclear/unintelligible — via encryption, masking, pseudonyms
SegmentationDivides network into segments, each with own controls; stops lateral movement; limits breach damage
Permission restrictionsACLs / RBAC — limit access to those who need it (least privilege)

⚠️ Trap trio: encryption is reversible, hashing and masking are one-way. Tokenization is reversible only via the token vault (separate DB). Masking vs tokenization: masking permanently replaces (de-identification); tokenization substitutes and keeps the original safe elsewhere.

7. Data Loss Prevention — DLP (4.4)

DLP = a strategy ensuring sensitive/critical information doesn't leave the organization, intentionally or unintentionally — detecting breaches/exfiltration. Why it matters: data theft evolved filing cabinets → laptops → external drives → thumb drives → cloud sync (Dropbox/Google Drive) — data and IP are "the currency of business."

The four DLP types (2.4-level memorization):

TypePlacementWatches
Endpoint DLPSoftware installed on workstation/laptopData in use — blocks or alerts on file transfers per rules (like an IDS/IPS focused on data); detection mode or prevention mode
Network DLPHardware/software at the network perimeterData in transit — all traffic in/out, special focus on outbound data that shouldn't leave
Storage DLPSoftware on servers in the data centerData at rest — inspects stored (often encrypted/watermarked) data; catches odd access like bulk downloads at 2 a.m.
Cloud-based DLPSaaS, part of the cloud serviceData stored in cloud services (e.g., Google Drive DLP)
8. Configuring a DLP (4.5) — from the Google Workspace demo

Console path (Google Workspace): admin.google.com → Security → Access and data control → Data protection. (Gmail DLP lives separately: Apps → Google Workspace → Gmail → Compliance → Content compliance.) Office 365 is a similar process — concepts matter, not clicks.

Rule-building flow (the exam-relevant skeleton):

  • Name + description — e.g., "Block SSNs: prevent SSNs from being shared in chat or Drive."
  • Scope — who the rule applies to (default: everyone; can target groups, e.g., instructors only).
  • Apps — Google Chat (messages + file uploads; OCR checks uploaded photos, e.g., a picture of an SSN card) and/or Google Drive.
  • Conditions — what to scan for: predefined data types (per-country: US SSN, driver's license, passport…), text string, regular expression, or word list (e.g., codename "Operation Neptune").
  • Likelihood threshold — where actions kick in. ⚠️ Low = floods of false positives; for SSNs/phone numbers set high or very high. Also set minimum unique matches / match count.
  • Actions (per app) — Chat: warn the user / block the message / audit (log + notify admins); Drive: block external sharing / warn / disable download-print-copy for viewers & commenters; add a custom user message.
  • Alerting — severity (low/medium/high) reported to the security dashboard + alert center; optional email notifications.
  • Set to Active.

Gmail variant: outbound rule + predefined content (US SSN) + high confidence threshold + action: quarantine the message (or modify, route, mark as spam, encrypt, reject) + notify the sender.

Context matters: DLP engines score *likelihood* using surrounding keywords — "SSN 123-45-6789" = very likely; the bare number 123-45-6789 alone = low/unlikely (could be any ID). A malformed "jason@diontraining" (no TLD) isn't recognized as an email at all. Use the built-in DLP demo tool to test what gets caught.

Rapid-Fire Self-Test
  • Who decides a data item's classification? *(The data owner)*
  • Commercial classification levels low → high? *(Public, sensitive, private, confidential)*
  • Government levels low → high? *(Unclassified, SBU, confidential, secret, top secret)*
  • Which government level covers a soldier's medical record? *(Sensitive but unclassified)*
  • Which level: weapon system blueprints? *(Top secret — gravely damages national security)*
  • Which level: military deployment plans? *(Secret — seriously damages)*
  • What law releases government unclassified data to the public? *(FOIA)*
  • What does overclassifying cost you? *(Money, time, resources — everything protected at high level)*
  • Who can NEVER delegate privacy-breach accountability? *(The data controller)*
  • Who is hired to process data on the controller's behalf? *(The data processor)*
  • Who makes sure data actually gets labeled per policy? *(The data steward)*
  • What role is a system administrator? *(Data custodian)*
  • Who's on the hook when a breach exposes PII? *(The data privacy officer)*
  • Should IT own the data? *(No — the business side owns; IT custodians)*
  • Three data states? *(At rest, in transit/in motion, in use)*
  • Full disk vs partition vs volume vs record encryption? *(Whole drive / one partition / a set of files & dirs / specific fields in a DB record)*
  • Protecting data in transit? *(SSL/TLS, VPN, IPsec tunneling)*
  • What protects data in use? *(App-level encryption, access controls, secure enclaves like Intel SGX)*
  • PII vs PHI? *(Identifies an individual / health info linked to an individual, HIPAA-protected)*
  • Which standard governs cardholder financial data? *(PCI DSS)*
  • GDPR protects EU citizens where? *(Within EU/EEA borders)*
  • Which two countries demand in-country data storage? *(China and Russia)*
  • Hashing vs encryption? *(One-way fixed-size / reversible with key)*
  • Tokenization's original data goes where? *(A separate, secure database — used for payment cards)*
  • Masking is what kind of process? *(One-way de-identification that can preserve format)*
  • Segmentation stops what? *(Lateral movement between network segments)*
  • Four DLP types? *(Endpoint, network, storage, cloud-based)*
  • Endpoint DLP watches which state? *(Data in use)*
  • Storage DLP catches what odd behavior? *(Bulk downloads at 2 a.m. from servers)*
  • Why not set DLP threshold to "low"? *(False-positive flood)*
  • Gmail DLP lives under which menu? *(Compliance → Content compliance)*
  • What raises an SSN match from low to very likely? *(Context keywords like "SSN")*
